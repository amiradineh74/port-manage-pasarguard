# معماری و تصمیم‌های طراحی

## چرا Agent نداریم؟

PasarGuard Node خودش در API `GetStats` نوع `Inbounds` را پیاده‌سازی می‌کند؛ افزودن سرویس جدید روی نودهای تولیدی ریسک نگهداری را زیاد می‌کند. جمع‌آورنده روی سرور مرکزی با `docker exec` یک **پروسه موقت جدا** در محیط پایتون فعلی کانتینر پنل اجرا می‌کند، بدون نصب فایل/کتابخانه و بدون تغییر پروسه اصلی پنل.

## شناسایی پایدار نود هنگام تغییر IP

از `Node ID` دیتابیس مرکزی PasarGuard برای انتخاب نود استفاده می‌کنیم، نه IP یا Tag. در هر بار جمع‌آوری، آدرس و مشخصات اتصال فعلی با `SELECT` خوانده می‌شود. اگر IP در همان رکورد تغییر کند، شمارنده جدید به‌عنوان baseline در نظر گرفته می‌شود تا جمع‌شدن مصرف دو سرور مستقل باعث محاسبه اشتباه نشود. هنگام حذف و ایجاد دوباره نود ممکن است Node ID تغییر کند و نیاز به انتخاب مجدد باشد. اطلاعات قبلی دیتابیس مستقل حذف نمی‌شوند.

## جهت و واحد اندازه‌گیری

`uplink/downlink` نام‌های برگشتی Xray برای اینباند هستند؛ مستقل از مفاهیم ترافیک شبکه سمت ارائه‌دهنده. یک GB در محاسبات مالی دقیقاً ۱۰۰۰۰۰۰۰۰۰ بایت است. خروجی raw بر حسب بایت، delta بر حسب بایت و هزینه به صورت اعشاری تومان ذخیره می‌شود.

## ساختار داده

`port_state`: شمارنده خام آخر، مجموع delta از شروع ثبت، آخرین نام نود و آخرین Tag.

`samples`: داده خام همان لحظه، اختلاف نسبت به نمونه قبلی، بایت مشمول هزینه، نرخ و هزینه نمونه در زمان ثبت، وضعیت baseline/reset/tag_changed/address_changed/partial.

`metadata`: نام نمایشی، ارائه‌دهنده، قیمت، جهت هزینه، مرجع شروع گزارش و نمایش/عدم نمایش در جمع.

`poll_runs`: زمان هر نمونه‌برداری و هشدارهای نودها.

## استقلال

هیچ دستوری برای دستکاری حجم، ریست حسابداری، ساخت کاربر یا توقف سرویس ارسال نمی‌شود. برای اتصال از کتابخانه داخل کانتینر موجود استفاده می‌کنیم. جمع‌آورنده روی میزبان دسترسی Docker دارد، اما HTTP server با کاربر جدا و محدود اجرا می‌شود.

**نکته نسخه:** مسیرهای Python و اسامی DB جدول‌ها در ارتقاهای آتی PasarGuard ممکن است تغییر کنند؛ تست روی نسخه جدید قبل از آپدیت ضروری است.
